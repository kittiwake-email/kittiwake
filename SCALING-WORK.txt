Attachment design:
- One scalar counter per distinct attachment hash in a mailbox's bounded index
  maps; live and retained messages share it. Message records carry forward refs.
- Append and retention removal change counts in their existing root journal,
  so crash recovery/retries do not require per-message attachment receipt keys.
- Upload reserves a zero-count generation before writing its immutable payload.
  A mailbox upload epoch fences collectors racing not-yet-reserved uploads.
  Retirement removes the counter, then deletes only its specific generation.
- Payloads have no OMAP. Deduplication is within a mailbox, deliberately spending
  disk capacity to avoid cross-mailbox counter contention on popular content.
- SQL GC candidates are transient and fenced against concurrent enqueue.
  Periodic payload sweeps recover crashes between retention commit and enqueue.

Validation and evidence:
Full unit/race suites, go vet and go build passed. The final query change also
passed its mailbox/JMAP race suites. The lab test playbook passed unit, MariaDB
and real-RADOS conformance. Ceph recovery, bounded maps, retention ranges, audit
segments, capability/capacity probes and attachment GC races passed. Protocol
verification passed SMTP/LMTP, IMAPS, POP3S, JMAP and SMTP submission. JMAP outbound
verification used only the lab's own recipient.

The live concurrent-ingestion test delivered 480 messages sharing one 16 KiB
attachment: eight mailbox counters [270,30,30,30,30,30,30,30], exactly eight payload
objects and zero payload OMAP keys. Every sampled MIME reconstruction matched.
Eight clients: 35.49 messages/s in one mailbox versus 95.08 across eight mailboxes.
This is a small workload comparison, not a cluster-capacity claim.

Remaining operating limits:
- A mailbox root serializes its mutations; the contention test exposes this.
  The lab has three replicated OSDs, so distributing primaries does not avoid
  writing all replicas. No million-mailbox throughput claim is established.
- Capacity placement uses raw cluster headroom, not per-OSD fullness, CRUSH pool
  quotas or measured IOPS. Automatic mailbox migration is not implemented.
- Folder and retention ranges cap key counts at 65,536; unlike capped maps/audit,
  their byte totals depend on record size. Large headers/attachment arrays need
  monitoring. Empty index/audit segment objects retain stale-writer fences.
- IMAP sessions still need O(message-count) compact metadata. General filtering
  scans folder pages; deep offsets, unlimited results and thread collapsing can
  require proportional memory. A search backend remains future work.
- Bulk mutation APIs, parallel storage sweeps and detailed contention metrics
  remain further throughput work, not requirements proven by these benchmarks.
